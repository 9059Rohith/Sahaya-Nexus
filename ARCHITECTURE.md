# Architecture

Sahaya is a modular monolith: one FastAPI service, one Next.js frontend and one relational database. The frontend uses a same-origin route handler as its backend-for-frontend layer. Python modules separate configuration, ORM models, Pydantic schemas, routes, authentication and deterministic business services.

The request state machine is `SUBMITTED → UNDERSTANDING → VALIDATION → VERIFICATION → PRIORITIZATION → MATCHING → ASSIGNED → IN_PROGRESS → ACTION_COMPLETED → OUTCOME_VERIFIED → IMPACT_RECORDED`. Side states include cancellation, rejection, expiry, duplicate and escalation. The backend rejects skipped stages. Verification is an explicit staff decision. Assignment requires a verified, available organization resource or volunteer. Impact requires an outcome submitted by the responder and confirmed by the requester.

`request_events` and `audit_logs` are append-only through the application API. The UI does not infer verification or impact from a status label. Matching uses administrator-configured weights for category, distance, availability, reliability, urgency fit, capacity and response history. Reliability and response history are derived from actual assignments and verified outcomes; a candidate with no history gets a neutral score. Its component scores and explanation are returned to the operator and the explanation is stored with the assignment. Operational maps round coordinates before making a request to OpenStreetMap.

SQLite provides a zero-service local development path. Docker uses PostgreSQL 17 with PostGIS 3.5. Alembic revisions are the schema source of truth. The PostGIS migration creates point geometry columns, triggers and GiST indexes for users, resources and requests; matching uses `ST_DWithin` when available and a geodesic fallback otherwise. Evidence files and the optional speech model are stored outside the web root in a mounted volume.

Resource capacity changes are recorded with the actor and linked request when assignments reserve or release capacity. The maintenance worker runs once per minute against the same database. It expires food requests after their stated safe-until time and escalates unresolved requests after the configured threshold. Its internal system actor makes these transitions auditable; the actor account has no login path. Staff can create a linked follow-up request without erasing the original timeline. Resource assignment reserves reported capacity and releases it when work closes. In-app notices are persisted in the database and scoped to their recipient.

The public issue explorer returns only opted-in, verified community/accessibility reports with allowlisted issue types and rounded coordinates. The public impact map aggregates recorded outcomes by 0.1° grid and suppresses cells below three outcomes. The browser service worker caches only static offline assets, never API responses or authenticated pages. Draft text and accessibility preferences live in local device storage.
